# 宝螺 Agent 化改造 — 可行性方案

> 问题：能不能把宝螺从「传统软件」做成「agent 软件」——我发一句命令，它自己调 API / 跑脚本把事办了，还更省 token、更高效？

**结论：可行，而且宝螺比大多数软件都更适合改。** 它现在的结构本来就是「引擎 + 遥控器」：
重活全在主进程（下载、Whisper 转写、Edge TTS、ffmpeg 合成、变声），渲染层只是个遥控器。
把遥控器换成 agent，是加一层皮，不是重构。

但「用脚本所以省 token」这句话只对了一半，下面第二节单独说清楚，这决定了方案怎么做。

---

## 一、现状盘点（为什么说适合）

| 事实 | 证据 | 对 Agent 化的意义 |
|------|------|-------------------|
| 主进程已有 70 个 IPC 处理器 | `src/main/ipc.ts`（1109 行，70 处 `ipcMain.handle/on`） | **这就是一张现成的工具表**，只是缺 name / description / 参数 schema |
| IPC 通道已按领域命名并分文件 | `media:*` / `transcribe:*` / `dialogue:*` / `local-tts:*` / `voice-convert:*` / `asr:*` / `hot:*` / `story:*` / `sniff:*` | 天然的工具分组，直接能映射成工具类别 |
| 长任务已有进度事件和取消 | `transcribe:progress`、`dialogue:progress`、`download:progress`、`story:progress`、`*:cancel` | 异步任务模型现成，不用新造 |
| 已有 DeepSeek 接入 + Key 管理 | `src/main/storyboard/ai.ts`、`src/main/sniff/analyzer.ts`、设置页「AI 服务」 | 不用新建 AI 基础设施 |
| 已有本地持久化 | `userData.ts`、`storyboard/store.ts`、`dialogue/settings.ts` | 会话、任务记录有地方放 |

一句话：**宝螺缺的不是能力，是「自然语言入口 + 编排层」。**

---

## 二、先把 token 这件事说对

你的直觉里有两个点，一个成立一个不成立。

### 成立的：脚本 / 程序化编排确实能大幅省 token

对比这两种做法，同样完成「下载 → 转写 → 写脚本 → 合成视频」：

| 做法 | 模型交互 | 大致开销 |
|------|----------|----------|
| A. 传统 tool-calling agent：模型每步决定调哪个工具，每步结果回填上下文 | 8~15 轮 | 高，且随中间产物膨胀 |
| B. 程序化编排（CodeAct 思路）：模型只输出一份计划，多步执行交给一段脚本跑，只在需要判断处回调 | 1~3 轮 | 低一个数量级 |

三个具体省钱杠杆：

1. **编排下沉**：让脚本跑循环，模型只做规划，不逐步参与执行。
2. **确定性流程固化**：固定套路（下载→转写→写脚本→成片）直接写成「剧本/工作流」，模型只负责识别用户意图选剧本 + 填参数，**中间零推理**。
3. **结果本地过滤 + 摘要回灌**：转写出来 5000 字，只把摘要和结构化字段放回上下文，原始文本落盘。模型永远不接触大产物。

### 不成立的：token 大头不是工具调用，是上下文

工具调用本身的开销很小。真正烧钱的是**每一步的中间结果反复塞回对话历史**——转写全文、解析出的 JSON、ffmpeg 日志。

所以「用脚本省 token」的正确版本是：**把昂贵推理压缩到少数几个决策点，其余交给确定性代码。**

反过来也提醒一句：如果做成「模型一步一步调工具、结果全回填」的朴素 agent，**会比现在更贵、更慢，还更容易跑偏**。方向要对。

## 三、建议的形态

三种可选形态，不是三选一，是分层：

| | 形态 | 说明 | 面向谁 |
|--|------|------|--------|
| A | **内嵌指令面板** | 界面上加一个聊天/指令框；模型 = 规划器，工具 = 现有 IPC | 最终用户，最小改动 |
| B | **本机服务（HTTP / MCP）** | 宝螺变成一台「能力服务器」，外面用 Claude Code / Codex / 自己的脚本驱动 | 你自己，复用性最高 |
| C | **CLI** | `baoluo run "把这个链接转成对话视频"` | 批量、自动化 |

**推荐 A + B，而且先抽出工具层。** 抽出「工具层」之后，A / B / C 都只是这层的消费者，C 几乎是免费得到的。

```
用户指令（自然语言）
  └─ Planner（模型）          ← 全流程唯一花 token 的地方
        ├─ 剧本匹配            ← 命中内置 workflow：0 token 跑完多步
        └─ 工具调用            ← schema 校验 → 直连现有 main 函数
              ├─ parser / downloader        下载、解析分享链接
              ├─ transcribe                 Whisper 转录
              ├─ tts / voice-convert        合成 / 变声
              ├─ compose                    ffmpeg 拼片
              └─ storyboard-ai / sniff      调 DeepSeek 写脚本、拆解爆款
  └─ 结果：结构化摘要回上下文，原始产物落盘
```

工具层的关键约定：**Planner 只能看到 `{ ok, outputPath, summary, jobId }`，看不到原始大内容。**

## 四、落地路线

### 阶段 0：抽工具层（1~2 天）

新建 `src/main/agent/tools.ts`，定义：

```ts
type ToolDef<P, R> = {
  name: string;            // 如 "media.download"
  description: string;     // 给模型看的一句话
  schema: z.ZodType<P>;    // 参数校验
  heavy?: boolean;         // 长任务，走 jobId 异步
  run: (p: P, ctx: ToolCtx) => Promise<R>;
};
```

把 8~10 个核心能力注册进去（`media.parse`、`media.download`、`transcribe.run`、`dialogue.compose`、`voice.synth`、`voice.convert`、`story.generate`、`sniff.run`）。
**IPC 处理器改成转发到 registry**，UI 一行不用动。这一步做完，行为零变化，但工具层已经存在了。

### 阶段 1：工作流引擎 + 指令面板（3~5 天）

- 写 3 条硬编码流程作为「剧本」：
  1. 链接 → 视频原片 mp4 + 文案
  2. 主题 → AI 对话脚本 → 配音成片
  3. 音频 → 变声 → 导出 mp3
- 渲染层加指令面板，先不做模型规划，用规则匹配剧本也能跑通端到端。
- 这一步结束就能演示「发一句命令，它自己把事办了」，且**几乎不花 token**。

### 阶段 2：模型规划器（3~5 天）

- 接 DeepSeek 函数调用（或 JSON 输出 + schema 校验 + 失败重试）。
- 上下文策略：滚动摘要 + 工具结果只留摘要 + 大产物落盘引用。
- 兜底：规划失败时回落到剧本匹配，而不是给用户报错。

### 阶段 3：对外开放（可选，3~5 天）

- 起一个本地 HTTP / MCP 出口，暴露同一份工具表。
- 你就可以用任何外部 agent 驱动宝螺，宝螺对外是「工具」，对内还是那个桌面软件。

## 五、真正的坑（按重要性排序）

1. **UI 依赖会卡死流程** —— `*:chooseFile`、`dialogue:chooseImage`、`app:chooseSavePath` 是原生弹窗，agent 调不了。必须补「参数化路径」版本，否则流程跑到一半停住等人点确认。**这是最大的改造点，工作量大头在这。**
2. **长任务必须异步化** —— 转写/合成要几分钟，工具层应返回 `jobId` + 订阅进度，不能 `await` 到底。已有 `*:progress` 通道，改造成本低。
3. **危险能力收口** —— 下载、删除模型（`local-tts:deleteModel`）、写盘路径需要白名单 + 确认。否则一句提示词注入就能删文件。
4. **幂等** —— 模型可能重复触发合成，白等几分钟。工具需幂等或提供 dry-run。
5. **规划用便宜模型** —— 路由和参数填充用 `deepseek-chat` 足够，别拿贵模型做分诊。

## 六、工作量与建议

| 阶段 | 工期（单人） | 产出 |
|------|--------------|------|
| 0 工具层 | 1~2 天 | 架构就位，行为不变 |
| 1 剧本 + 指令面板 | 3~5 天 | 可演示的 POC |
| 2 模型规划器 | 3~5 天 | 真·自然语言驱动 |
| 3 对外开放 | 3~5 天 | 可被外部 agent 调用 |

**POC（阶段 0+1）约 1 周，完整形态约 3 周。**

建议先做阶段 1 的三条剧本——它能立刻落地「我发命令它干活」，而且因为流程是硬编码的，token 消耗接近零。等这个跑顺了，再上模型规划器处理长尾指令。

---

## 一句话总结

可行。省 token 的关键不是「用脚本」，而是**把推理压缩到少数决策点 + 把确定性流程固化**；
宝螺已有 70 个 IPC 能力和一整套异步任务通道，改造重点是补齐「无 UI 的工具接口」，而不是重写业务。
