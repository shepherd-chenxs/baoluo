
## v0.9.0 —— 2026-09-30 · 变声器上线 · 视频生成拆两页 · 数据目录可换盘 · 移除素材捕手

> 涉及：[voice-convert.ts](../src/main/dialogue/voice-convert.ts)、[VoiceConvertView.tsx](../src/renderer/views/VoiceConvertView.tsx)、[userData.ts](../src/main/userData.ts)、[DialogueView.tsx](../src/renderer/views/DialogueView.tsx)、[composer.ts](../src/main/dialogue/composer.ts)、[ipc.ts](../src/main/ipc.ts)、[installer.nsh](../build/installer.nsh)、[http.ts](../src/main/http.ts)、[sniff/pipeline.ts](../src/main/sniff/pipeline.ts)、[agent/router.ts](../src/main/agent/router.ts)
> 设计与调研过程：[变声器功能-产品设计.md](./变声器功能-产品设计.md)、[变声器功能-开源方案调研.md](./变声器功能-开源方案调研.md)、[数据目录迁移-方案讨论.md](./数据目录迁移-方案讨论.md)

**1) 新增「变声器」**　上传音频或视频 → 抽人声 → 识别文案 → 用指定音色逐句重念 → 拼成一条音频。全流程四阶段可见（提取人声 / 识别文案 / 逐句配音 / 拼接），识别时滚动显示实时文本、配音时报「第 n/共 m 句」，另有一个跳动的「已用时」避免误以为卡死。音色可选在线（Edge，可调语速/音调/音量）或本地克隆（滑杆置灰，参数由模型决定），结果可试听、「保存为 MP3」（自动转码）或打开所在文件夹。

实现上顺带抽出了 [clone-voice.ts](../src/main/dialogue/clone-voice.ts)（克隆音色的公共辅助，语音合成与视频生成也改用它），并给 [transcribe.ts](../src/main/transcribe.ts) 加了 `onProgress` 回调——变声器有自己的 `voice-convert:progress` 通道，转写进度不会串到语音识别页的界面上。

几个踩过的坑：克隆音色输出 32kHz wav、在线音色输出 24kHz mp3，拼接前统一转成 32kHz/单声道/pcm_s16le 再走 concat；单句合成失败只跳过该句，最后报「成功 x/共 y 句」，全部失败才报错；切句与归一化的中间产物跑完就删，用户目录里只留一条 `voice.wav`；旧结果只保留最近一次，与语音合成一致。

**2) 「视频生成」拆成两个子页面：图文解说 / 对话模式**　侧边栏「视频生成」改为可展开的目录项，下分两页，各自记各自的模板配置与脚本草稿（草稿键按模式分开）。老用户存的 `activeTab = "dialogue"` 会自动迁移到「视频生成 → 对话模式」，不会因为改名掉回默认页。

**图文解说**改为与「热点成片」一致的分镜模式：**一个镜头 = 一张图 + 一段解说词 + 一个解说员**。音色与语速/音调/音量在镜头卡片里单独设置，每镜有试听喇叭，运镜也逐镜配置，图片可直接拖进图框；另加了一个从右侧滑出的「字幕文案」抽屉，把每镜解说词拉到一屏里改。想在同一段里换音色，拆成两个镜头即可。

随之而来的一条规则变化：**解说模式不再解析「角色名：」前缀**——音色由镜头配置决定，所以整行照念（`解说员A：你好` 会把前缀也念出来），原先那两条「第 3 个及以上角色名」「未使用角色名」的警告也一并去掉；对话模式解析规则不变。合成时按 `imageNarrators[i]` 取音色，缺省才回退到全局音色。

**3) 数据目录可换盘（默认从 %APPDATA% 挪到 C:\Baoluo\data）**　原来的数据都堆在 `%APPDATA%\Baoluo`，实测约 **5.3 GB**（Genie 模型 4.08 GB + 便携 Python 720 MB + whisper 模型 141 MB）。现在设置 → 通用设置 → 数据目录里会显示当前目录与占用大小，点「更改…」选一个新盘目录 → 确认 → 带进度复制 → 「立即重启生效」。

- **老用户不吃亏**：目录里只要有 `settings.json` / `genie` / `models` / `runtime` 任一，就就地认领 `%APPDATA%\Baoluo`，不改默认值等于不把模型、设置全丢了。
- **指针文件** `data-root.txt` 必须留在默认目录（数据搬走后只有这里知道数据在哪），新旧两个默认位置都认；指针里的目录不存在（比如移动盘没插）就自动回退默认目录，不让应用起不来。
- **迁移策略**：复制 → 校验 → 写指针 → 清空旧目录。中途失败旧数据完整、下次启动仍走旧目录；迁移前用 `fs.statfsSync` 比对目标盘可用空间，不够直接拦下；目标目录不能与当前目录互相包含，避免越拷越多的递归。
- **顺手解决的**：Chromium 缓存用 `--disk-cache-dir` 指到 `<数据目录>/cache`（C 盘少 268 MB）；启动时清掉老版本遗留的 `video2c-tmp`；卸载脚本改为先读指针文件，勾选「清除应用数据」时把自定义目录一起删干净。
- **删不掉的下次再删**：Genie 服务与 Chromium 占着的文件当场删不干净，会记进 `pending-cleanup.txt`，下次启动早期（还没人占用）补删一次。
- **开发模式下「立即重启」不真重启**：`app.relaunch()` 会把 vite 一起带走导致白屏，现在只在正式版重启，开发模式提示手动重启。

**4) 字幕与成片质量修复**

- **字幕底色默认「无色」**，背景透明度的语义也修正为「1 = 完全透明」；顺手新增 [ColorPicker.tsx](../src/renderer/components/ColorPicker.tsx)，底色多一个「无色」选项。
- **裁掉句尾静音**：Edge 返回的音频尾部自带约 0.9 秒静音（实测 -91dB），不裁的话每句多近 1 秒死时间、字幕还会一直挂到静音结束。在线音色按词级时间轴裁（首尾各留 120/150ms 余量，本来就没多少静音就跳过转码）；克隆音色没有逐词时间轴，改用静音检测裁尾（[audio-silence.ts](../src/main/dialogue/audio-silence.ts)）。
- **卡拉 OK 填充不再「慢半拍」**：词只按自己的时长填充，词后的停顿用一个「空 k」占位。原来停顿被并进这个词的填充里，读音早停了、填充还在慢慢爬，停顿越长越像字幕跟不上。
- **时间轴对不上文本就退回按文本拆**：字幕文字只从词级时间轴拼，一旦两者不是同一句（例如沿用了别的镜头的音频）就会整句张冠李戴。现在先比对（去空白后取 LCS，相似度 ≥ 0.8 才采信），不合就丢掉时间轴、退回按文本拆字幕。
- **句间补真实静音**：同场景内两句之间插入 0.3 秒静音。字幕时间轴本来就按「上一句时长 + 该停顿」推进，音频不真插静音的话，拼接后的声音没有间隔，字幕会从第二句起越来越晚。
- **静止画面段改用 zoompan 复制帧**：单帧输入没有 `-loop` 时，一整段只有 1 帧，单段还能靠 `-t` 撑住，多段走 xfade 时直接产出坏视频（实测只剩 0.6 秒 / 2 帧）。
- **克隆音色用完就卸载**：Genie 每次 `load_character` 都会新加载一份几百 MB 的 ONNX 模型，连续生成几次会 OOM，表现为合成出空音频片段。现在每组（同一克隆音色）用完 `unloadCharacter`。
- **合成失败提示具体到第几句**：原来只报「有 N 句失败」，现在列出失败的是第几句（超过 3 句省略）。
- 文件系统错误转成人话（[fsError.ts](../src/main/fsError.ts)）：输出目录没权限或磁盘满时给可操作的提示，而不是一串英文错误码。

**5) 其它小修**

- `AppSelect` 下拉按最长选项撑开宽度，再把左右收进视口，`无（静止）` 这类标签不再折行。
- 克隆音色页：删掉的正好是当前试听的音色时，播放器一起收掉，不留「已删除音色」的试听。

**6) 移除「素材捕手」（多平台视频解析下载）**　开源前评估风险时确认：这一块的实现手段（复刻平台接口签名、用隐藏窗口 + DevTools 协议截获页面自己发出的详情请求、改写播放地址）属于"规避平台技术措施"，与是否营利、是否开源无关，公开源码只会让这部分的认定更直接。因此整体移除，不再提供从平台取内容的能力。

删掉的东西：`src/main/parser/`（douyin / kuaishou / bilibili / xiaohongshu / extractUrl / pickFields / html）、`src/main/downloader.ts`、`src/renderer/views/MaterialView.tsx`，以及 `media:parse` / `media:download` / `media:autoSavePath` / `media:defaultSaveDir` / `media:openDir` / `app:chooseSavePath` / `app:chooseMaterialsDir` / `app:suggestFileName` 这一批 IPC 与 `window.materials` 整个 API 面。

## v0.8.14 —— 2026-09-20 · 模型库只报状态，不显示下载进度

> 涉及：[ClonePage.tsx](../src/renderer/views/settings/ClonePage.tsx)（回到只显示状态字）
> 沿用了 v0.8.13 已有的机制：[genie-manager.ts](../src/main/dialogue/genie-manager.ts)、[ipc.ts](../src/main/ipc.ts)、[dialogue-types.ts](../src/shared/dialogue-types.ts)（`percent` 照旧随进度事件上报，只是界面不再显示）

**结论先行**　模型库那行的下载状态就是三个词：**`已下载 / 下载中… / 未下载`**。不显示百分比、不显示细节、不弹浮层、不占屏幕——点完下载该干什么干什么，需要取消时入口就在状态旁边（「取消」按钮）。

**试过再加进度，最后决定不加**　中间做过一版「下载中 43%」+ 悬停显示"正在处理文件 N/M"，真机对比之后撤掉了。原因：

- 用户点下载时不打算盯着数字看。后台下载的意义就是不必守着，加个百分比等于把人拽回来。
- 这个百分比**本身信号质量就不好**，做了也得打折扣：它只是"当前那一批传输"的进度——**安装依赖**（pip，首次几分钟）与**连接下载源**阶段根本拿不到（真机实测连着 66 秒一条带数字的事件都没有）；**续传会严重低报**（见到提示已到「正在处理文件 9/13」而 percent 才 1%）；还可能**先到 100% 再继续下一个仓库**。要显示成"能用"的样子，得额外加：1MB 采样门槛、`n ≥ total` 不采信（汇总条的"已发现总量"会随文件发现而变大，续传时先遇到已在盘上的大文件会直接算成 100%，一旦采信就会把整轮钉死在 99%）、高水位只增不减（真机抓到过 `99% → 1% → 0%` 的回退）、封顶 99%。**一堆补丁只为显示一个不该被盯着的数字，不如不显示**——判断"是不是卡死了"有更直接的办法：v0.8.11 的 30 秒读超时（`HF_HUB_DOWNLOAD_TIMEOUT`）与 v0.8.13 的 120 秒无数据断开，死连接会自己换源或报错，不需要用户盯着数字判断。
- 需要看细节时，`install.log` 与控制台里有完整留痕（原始输出含本机路径与模型仓库地址，按 v0.7.3 的规矩不上界面）。

**为这版改过的东西已全部撤回**：`src/shared/local-tts-status.ts`（新增的共享模块）、`scripts/test-local-tts-status.cjs`（38 条断言）、`styles.css` 里为数字不抖动加的 `min-width: 84px`、以及主进程里那套采样/高水位计算，都已删掉，`percent` 回到 v0.8.13 的原样上报（界面不消费）。仓库里没有留下"试过但没用上"的代码。

**验收**

**排查记录：模型文件"莫名消失"是杀软隔离，不是应用缺陷**　本机验证期间三个模型目录（含 700MB 便携运行时）整个消失过，一度怀疑应用里有删除逻辑。逐条查证后确认**不在应用侧**：

## v0.8.13 —— 2026-09-20 · 声音克隆下载改为后台下载（不打扰）

> 涉及：[genie-manager.ts](../src/main/dialogue/genie-manager.ts)、[ipc.ts](../src/main/ipc.ts)、[index.ts](../src/main/index.ts)、[preload/index.ts](../src/preload/index.ts)、[dialogue-types.ts](../src/shared/dialogue-types.ts)、[ClonePage.tsx](../src/renderer/views/settings/ClonePage.tsx)、[styles.css](../src/renderer/styles.css)

**改前的问题**　点「下载」后，渲染层一直 `await` 到下载结束——首次使用要下运行时 + 装依赖 + 下模型，**几分钟里界面只能干等**：切走页面就不知道还在不在下，想干别的也不行。

**改法：任务归主进程，界面全程不打扰**

- `startDownloadInBackground()` 受理后**立即返回**，任务由主进程继续跑；进度改为**广播给所有窗口**（不再只发给发起方），结局新增 `local-tts:taskDone` 通道。

- 进度与状态**只体现在模型库那一行**：`已下载 / 下载中… / 未下载`；下载中的那条操作列是「取消」，其余模型的「下载」置灰（不并发）。模型库卡片里原有的进度条（`.local-progress` 区块及其样式）整块删除，`styles.css` 因此少 58 行，界面上不再有第二处进度。

**模型库改为以主进程为真源**　它原来只在"本地 `downloadingKey` 有值"时才轮询任务快照，于是任务若不是本组件发起的（切页面回来晚了、错过开局），列表会显示成「未下载」+ 可点的下载按钮，点一下就可能并起第二个下载进程。现在改为**常驻 2 秒轮询** `local-tts:task`（只读内存、不起子进程，很便宜），状态一律以主进程为准；只有任务收尾那一刻才调一次 `env()` 把「已下载」标记刷出来。

**顺带修掉的几个坑**（都是"后台化"之后才会被放大的）

- **卡死连接**：运行时归档下载（走 `https.get`，没有子进程）此前只按"收到数据时检查取消标记"，连接建上但对端不发数据就会**永远挂着**，而后台下载没有界面参与，更没人会发现。现在 120 秒无数据即主动断开报错，并在收到数据时重排计时。

**验收**

- `npm test` 新增 17 条断言（共 51 条）：受理即返回、快照立即可见、同模型并入 / 换模型同步拒绝、取消立即收尾且不进下载步骤、成功/取消/失败三种结局都通知到且不残留任务状态、`shutdown()` 不抛错。已用变异测试确认：把 `startDownloadInBackground` 改回阻塞、或收尾不清 `downloadTaskKey`，该脚本都会 FAIL。

## v0.8.10 —— 2026-09-11 · 修掉安装完成后的卡死（真机复现定位）

> 涉及：[genie-manager.ts](../src/main/dialogue/genie-manager.ts)

**真机复现**　在安装版 0.8.9 上用 DevTools 协议直接调 `window.localTts.download('feibi')`（genie_tts 缺失，强制走安装分支）：pip 依赖**已装好**（site-packages 141 项、genie_tts True），但主进程 4 秒吃掉 3.94 秒 CPU（≈100% 空转）、IPC 全部无响应、日志停在"开始下载任务"。开发环境不复现，因为开发态用 `resources/python` 里预装好的运行时，**根本不走"下载运行时 + pip 装依赖"这条路径**——这正是"开发没事、安装版必挂"的原因。

## v0.8.4 —— 2026-09-11 · 模型下载支持多源回退与断点续传

> 涉及：[genie-manager.ts](../src/main/dialogue/genie-manager.ts)

**现象**　在「声音克隆 → 模型库」点下载，报「语音模型下载失败，请检查网络后重试；如果一直失败，可以另外索取离线模型包。」反复重试无效。

**根因**　不是"网络不通"，是三件事叠在一起：

1. 到 HF 国内镜像（hf-mirror.com）的连接间歇性超时——实测 `[WinError 10060] 连接尝试失败`，能通时速度也在 0.45～2.2MB/s 之间大幅波动（对照：清华 PyPI 正常）。
2. huggingface_hub 1.x 在远端不可达、但 `local_dir` 已存在时，**只打一行 warning 就返回已有目录，不抛异常**。脚本照样 `exit 0` 并写 `ready.json`，主进程只能看到"关键文件仍不齐"，于是把网络问题报成泛泛的"请检查网络"。
3. 主进程每次下载前会清掉 `*.incomplete`，等于**没有断点续传**：慢网掉一次线就前功尽弃，146MB 的文件永远下不完。

**改动**

- `clearHfDownloadResidue()` 只清 `.lock` 与 0 字节的 `*.incomplete`；有内容的半成品保留，交给 huggingface_hub 续传（此前一并删除，是"每次重试都从零开始"的原因）。
- 下载源改为三个依次回退：`hf-mirror.com` → `aifasthub.com` → `hf-mirror.net`，`etag_timeout` 由 10s 放宽到 30s。生成脚本自带文件自检（9 个模型文件 + 4 个公共资源），任一源把文件下齐即成功，否则 `exit 3`。
- 失败文案带上原因：网络类失败显示「语音模型下载失败（下载源连接超时）…」；进度里不再透出镜像地址，控制台保留 exit code 与原始输出便于排查。

**验证**　离线模拟（三源依次失败 → `exit=3` → 文案带原因，4 秒）；真实下载（补齐 mika 缺失的 `t2s_shared_fp16.bin`，146MB / 65 秒 → `MODEL_READY`）。

## v0.8.3 —— 2026-09-11 · 修复首次使用声音克隆必然失败

> 涉及：[genie-manager.ts](../src/main/dialogue/genie-manager.ts)

**现象**　新装的打包版第一次在「设置 → 声音克隆」点下载，必定报「语音合成组件下载失败，请检查网络后重试；如果一直失败，可以提 Issue。」反复重试无效，跟网络无关。

**根因**　`downloadArchive()` 把运行时归档写进 `dest + ".part"`，写完后没有改名成 `dest` 就 resolve；紧接着 `ensureRuntime()` 执行 `tar -xzf python-runtime.tar.gz`，文件不存在，tar 退出码 1 → 抛「解压失败」→ 落到上面那句提示。下载其实是成功的：出问题的机器上留下了 39,291,615 字节的完整 `.part` 文件，手动改名后能正常解压出 `python/python.exe`。

**为什么 v0.8.0 起一直没暴露**　开发机的 `resources/python` 由 postinstall 装好，`ensureRuntime()` 开头的 `resolvePythonExe()` 直接命中并返回；只有安装包（extraResources 不含 `resources/python`）才会真正走下载分支，也就是说只有新用户会踩到。

**修复**

- `out.end()` 回调里 `fs.renameSync(tmp, dest)` 之后再 resolve（本体修复）。
- `downloadArchive()` 增加单次结算 `finish()`：此前取消时只 `destroy()` 不 `reject()`，Promise 永不结算，上层 `await` 一直挂着，界面卡在「正在取消…」。
- 进度文案「正在下载语音合成运行环境（仅首次，约 200MB）」改为「约 40MB」（该归档实际 37.5MB）。

**验证**　临时脚本（`tmp/`，不入库）用假的 `electron.app` 把 userData 指到临时目录、并藏掉随包运行时，强制走真实下载链路：37.5MB 下载完成 → 改名 → 解压 → `runtime/python/python.exe` 存在，耗时 13 秒；`tsc -p tsconfig.node.json` 通过。

**影响**　0.8.0 与 0.8.2 的安装包都有这个问题，建议尽快替换；0.7.x 及更早没有运行时下载逻辑，不受影响。

## v0.8.1 —— 2026-09-11 · 声音克隆下载任务改由主进程托管

### 声音克隆 · 点「下载」后切页面再回来，界面不再与任务脱节

> 涉及：[genie-manager.ts](../src/main/dialogue/genie-manager.ts) · [ClonePage.tsx](../src/renderer/views/settings/ClonePage.tsx) · [dialogue-types.ts](../src/shared/dialogue-types.ts)

**现象**　在「设置 → 声音克隆 → 模型库」点「下载」后切到别的页面，再切回来：进度条消失、模型状态变回「未下载」、下载按钮重新可点、「取消」按钮不见。

**根因**　下载本身一直跑在主进程的独立子进程里，切页面并不会中断它；丢的是**界面状态**。
`managerBusy` / `managerProgress` / `downloadingKey` 都是 `ClonePage` 的组件内 state，切页面即随卸载丢失，重新挂载只跑一次 `refreshEnv()` 也拿不回 busy。
后果不只是显示不一致：用户回来看到可点的「下载」再点一次，`prepare()` 没有并发守卫，会**真的起第二个下载进程**，并覆盖 `activeDownloadKey`，导致「取消」只能杀掉最后一个进程；两个 `snapshot_download` 还会抢同一份 `local_dir` 与 HF 缓存。

**改动**

主进程（`genie-manager.ts`）成为任务状态的唯一真源：

- 新增 `runDownloadTask()` 作为下载唯一入口，`download()` / `enable()` 均改走它；同一模型重复点击并入当前任务，换模型则直接拒绝（"已有模型正在下载…"），不再可能并行两个下载进程。
- 新增 `downloadTaskKey`（含装依赖阶段）与 `lastProgress`，由 `env()` 一并返回，界面据此恢复「下载中」。
- 取消流程重做：新增粘性 `cancelRequested`，在 `prepare()` 的运行时下载、依赖安装、模型下载三处设检查点。此前 `activeDownloadAborted` 会被各步骤自己清掉，导致"装依赖/解压阶段点取消"根本不生效，仍会继续装依赖、下模型；现在各阶段都可中断并统一收口到「下载已取消」。
- pip 安装子进程纳入 `activeDownload` 管理，取消能立即杀掉；`deleteModel` 的占用判断改用 `downloadTaskKey`。

渲染层（`ClonePage.tsx`）以主进程为准：

- 新增 `syncFromEnv()`：挂载时按 `downloadingKey` / `progress` 恢复 busy、进度条、「下载中…」与「取消」按钮；`state === "error"` 时把主进程的错误提示显示出来（此前切页回来失败是静默的）。
- 下载期间每 2.5 秒轻量对齐一次主进程状态（带并发保护、不叠加请求），任务结束或取消后自动恢复成「可下载」，不会卡在「下载中…」。
- 进度条渲染不再依赖组件自己的 `managerBusy && managerProgress`，改为"主进程有任务就显示"；任何任务在跑时，其他模型的下载按钮置灰。

类型（`dialogue-types.ts`）：`LocalTtsEnv` 增加 `downloadingKey: string | null` 与 `progress?: LocalTtsProgress | null`。

**验证**　`tsc -p tsconfig.json` / `tsc -p tsconfig.node.json` / `npm run build:renderer` / `npm run build:main` 全部通过。

**版本号**　0.8.0 → 0.8.1（当时仍需手工同步六处；v0.8.2 起改为单一来源）。

**已知边界**　退出整个应用仍会中断下载，且下次从零开始（重下前会清掉 HF 的 `.incomplete` 残留，不做断点续传）。

## 附录 · 版本号维护

**只有一处需要改**：`package.json` 的 `version`。

```bash
npm run bump -- 0.8.3     # 同时更新 package.json 与 package-lock.json
```

以下位置都是从它推导的，不要再手工写死（v0.8.2 起）：

| 位置 | 取值方式 |
| --- | --- |
| 窗口标题（`src/main/index.ts`） | `app.getVersion()` |
| 关于页（`AboutView.tsx`） | 构建时注入的 `__APP_VERSION__` |
| 渲染层 `index.html` 标题 | 不含版本号，仅兜底 |
| 安装包文件名 | electron-builder 按 package.json 生成 |

改完记得重新构建：渲染层的 `__APP_VERSION__` 是构建时注入的，`npm run dev` 需要重启。
