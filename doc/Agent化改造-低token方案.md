# 宝螺 Agent 化 — 低 token 方案

> 问题：怎么让宝螺变得很好用，同时几乎不烧 token？

**核心原则：最便宜的 token，是根本没发出去的那次请求。**

省 token 不是「让每次请求更便宜」，而是**让绝大多数操作压根不经过模型**。
下面是一条从上到下的漏斗，越靠上越便宜，目标是把 90% 的操作压在 0 token 层。

---

## 一、四层漏斗

```
第 0 层  确定性代码 / 规则        → 0 token    ← 目标：吃掉 90% 的操作
第 1 层  模型只做两件事           → 几百 token ← 歧义消解 + 参数抽取
第 2 层  上下文工程               → 决定成本   ← 真正的省钱大头
第 3 层  交互设计                 → 减少往返   ← 每少一轮 = 省一整份上下文
```

---

## 二、第 0 层：让大部分操作 0 token（最重要）

### 1. 用「轻量 DSL」替代自然语言

用户输入自带结构，就不需要模型去理解：

| 用户输入 | 识别方式 | 走的流程 |
|----------|----------|----------|
| `https://v.douyin.com/xxx` | 正则匹配 URL | 素材流程：下载 → 转录 |
| `把上面那个转成对话视频` | 指针词 + 上一轮状态 | 复用上一份产物，不调模型 |
| `@对话 事业运 女声` | `@` 前缀 + 位置参数 | 对话成片剧本 |
| `音色小美：大家好` | 冒号分段 | TTS 合成 |

**规则能做的一律不用模型。** 宝螺的输入类型其实很收敛：链接、主题词、脚本、文件路径。
四种输入用正则 + 关键词就能分对，正确率足够高。

### 2. 固定套路固化成「剧本」

凡是三步以上、每次都一样的流程，写成硬编码工作流：

1. **链接 → 视频原片 mp4 + 文案**（parse → download → transcribe）
2. **主题 → 对话脚本 → 成片**（story-ai → compose）
3. **音频 → 变声 → 导出**（voice-convert → save）

命中剧本后，**多步执行全程 0 token**，模型完全不参与。
真正需要模型的只有剧本里的那一次生成（比如写脚本），那本来就是业务必需的成本。

### 3. 本地能力优先

宝螺里已经有现成的 0 token 工具，别浪费：

- **Whisper** 做转写 —— 不要用模型「听写」
- **jieba**（`jieba_fast` 已在依赖里）做关键词/分词 —— 不要用模型「提取关键词」
- **ffmpeg** 做时长、静音检测（`audio-silence.ts`）—— 不要用模型「估算时长」
- **正则 / 截断 / 统计** 做摘要 —— 不要用模型「总结」

> 判断标准：**能用 20 行代码写死的，就不要写成提示词。**

---

## 三、第 1 层：模型只做两件事

当第 0 层认不出来时，才发一次请求，而且这次请求要**窄、短、结构化**：

1. **歧义消解**：用户到底想要哪条流程？输出一个枚举值。
2. **参数抽取**：主题是什么？音色选哪个？输出 JSON。

两条硬要求：

- **`max_tokens` 压到 256~512。** 现在 `src/main/storyboard/ai.ts` 的调用统一写了 `max_tokens: 4096`，路由类请求根本用不到，纯浪费预算上限。
- **`response_format: { type: "json_object" }`**（项目里已在用）+ schema 校验 + 本地重试。别让模型输出自然语言再解析。

模型选择：路由/抽取用 `deepseek-chat` 足够，**不要拿贵模型做分诊**。

---

## 四、第 2 层：上下文工程（真正的省钱大头）

这一层决定成本量级，比「用哪个模型」重要得多。

### 1. 大产物一律落盘，只回传摘要

工具层对模型只暴露：

```ts
{ ok: true, outputPath: "...", summary: "已下载 45s 视频，文案 213 字", jobId: null }
```

转写全文、抓取的 JSON、ffmpeg 日志 —— **一个都不进上下文**。
模型的上下文里永远只有路径和一句话摘要。

### 2. 绝不把全量工具表塞进 prompt

宝螺有 **70 个 IPC 处理器**。如果把每个都写成工具描述每轮发送，光工具定义就是几千 token，而且**每一轮都要重发**。

对策（按优先级）：

- 只注册 8~10 个「门面工具」，内部再分派（`media.*`、`compose.*`、`voice.*` 一级就够）
- 两段式：先让模型选类别，再只注入该类别的工具
- 工具描述写一句话，参数说明极简

### 3. 命中提示词缓存

DeepSeek 对相同前缀的上下文按命中价计费，明显更便宜。做法：

- **system 提示固定不动**，把变化的用户输入放在最后
- 不要在 system 里拼时间戳、随机 ID、当前状态 —— 一改前缀，缓存全废

### 4. 会话记忆用滚动摘要

- 只保留最近 2~3 轮原文
- 更早的压成一份**结构化状态对象**（当前项目、上次产物路径、已选音色），由代码维护，不花 token
- 不要让模型去「总结对话历史」—— 那是纯浪费

---

## 五、第 3 层：交互设计，少一轮就省一份上下文

1. **一次问清，别多轮追问。** 需要三个参数就弹一个小表单/参数预览条，而不是让模型问三次 —— 每次追问都是一整轮完整上下文。
2. **默认值必须足够好。** 音色、时长、字幕位置默认到位，用户不改就不需要模型介入。
3. **失败在本地重试。** 下载失败换源、合成失败重试，都是代码的事，不要回模型「问怎么办」。
4. **执行前给预览。** 展示「将执行：下载 → 转录 → 写脚本 → 合成」，用户点确认。省掉纠正性往返。

---

## 六、成本对比（估算）

场景：*「把这个抖音链接做成对话视频」*

| 方案 | 模型调用 | 输入 token | 输出 token | 说明 |
|------|----------|------------|------------|------|
| 朴素 agent（逐步 tool-calling） | 约 10 轮 | 每轮重发全量工具表 + 历史增长，累计 5 万+ | 数千 | 每步中间结果都回填 |
| **本方案（漏斗）** | 1 次路由 + 1 次写脚本 | 数百 + 约 800 | 数十 + 约 900 | 剧本执行 0 token |

**量级差约 20~30 倍**，而且链路越复杂差距越大。

---

## 七、落地清单

- [ ] 输入分流器：URL / 主题 / 脚本 / 路径 四条正则规则（0 token）
- [ ] 三条硬编码剧本 + 命中即执行
- [ ] 工具表收敛到 8~10 个门面工具，描述一句话
- [ ] 工具返回值统一为 `{ ok, outputPath, summary, jobId }`
- [ ] 路由请求 `max_tokens` 降到 512，走 `json_object`
- [ ] system 提示固定前缀，变量后置（吃缓存）
- [ ] 会话状态对象由代码维护，只留 2~3 轮原文
- [ ] 参数表单替代多轮追问
- [ ] **加 token 记账日志**：每次模型调用记录输入/输出/缓存命中，落进现有日志目录

> 最后一条是前提。**不量化就没办法优化** —— 先把每条流程花了多少 token 记下来，才知道该砍哪一刀。

---

## 一句话总结

好用和低 token 不矛盾：**让用户觉得好用的是「一句话就把事办了」，而不是「模型在思考」。**
把识别交给规则、把执行交给剧本、把生成交给模型，成本自然就摊薄到了只有真正必须的那一两次调用上。
